## 2. Previous accounting — what `1,457,486` actually was

**An ESTIMATE (category C).** In `_freeze_v6.py` the per-call input tokens were:

```python
in_tok = int(round(total_bytes * (V5A1_OBSERVED[arm] / v5a1_total_bytes)))
```

i.e. an **empirical bytes-to-token ratio** calibrated on six V5A.1 paid calls, then **`round()`ed** (so it could round down). The governing standard forbids an empirical/average ratio as the basis of a hard bound and forbids rounding a bound downward. It was a good forecast; it was **not** a mathematical upper bound on billable input tokens.

## 3. Final request construction — the one authoritative representation

`src/research/hypothesis_oos/v6_token_count.py::canonical_converse_request()` is now the **single** structure. It carries `modelId`, `system`, `messages`, `inferenceConfig`, `toolConfig`. Both:
- **token accounting / hashing** (`request_sha256`, `conservative_token_upper_bound`, `token_entry`), and
- **execution** (`_execute_v6.py::call_once` calls `client.converse(**canonical_converse_request(...))`)

use it. The driver rebuilds the same structure, re-hashes it, and compares against the frozen manifest before invoking — a mismatch raises `RequestHashMismatch` (a `TransportPreflightFailure`) and no Bedrock call is made. Previously token accounting hashed `system + NUL + user` while execution built a different structure with the tool schema — a drift surface, now removed.

## 4. Token-count method

- **Preferred (exact):** `bedrock-runtime:CountTokens` — provider-native, **non-generative, zero-charge** (AWS docs), returns the exact input-token count the model would charge for the same Converse input. Wired into `v6_token_count.count_tokens_exact` and used by the driver at run time to reconcile. `count_model_id` is the foundation-model id the inference profile resolves to (`us.anthropic.claude-sonnet-4-6` → `anthropic.claude-sonnet-4-6`; AUDIT 10, mapping frozen in the manifest).
- **Frozen bound (used now):** because `CountTokens` is not permitted for this role, the frozen ceiling uses the **UTF-8 byte length of the full canonical Converse token input** (system + messages + toolConfig), `method = "utf8_byte_upper_bound"`.
- **Why it cannot underestimate:** Claude tokenization is byte-level BPE — every token is ≥1 UTF-8 byte, so tokens ≤ text bytes; counting the bytes of the **entire** serialized request (including the JSON tool schema and message framing) dominates the small structural token overhead the server adds. No empirical ratio, no rounding down. It is loose (~2.8× the old estimate), which is the safe direction for a hard bound.
- The freeze makes **no network call** and is deterministic; the exact `CountTokens` value (when available at run time) can only be ≤ the byte bound, so using the byte bound in the frozen ceiling is conservative and safe.

## 12. Read-timeout wording correction (AUDIT 12)

The earlier phrasing "`read_timeout = 900` ensures a billed response is read" was too strong and is corrected in `v6_token_count.py` and `v6_transport.py`: a long read timeout **reduces the probability** of client-side abandonment but **cannot guarantee** network delivery. The cost guarantee rests solely on `total_max_attempts = 1` — even if an accepted, billed response is lost, V6 does not automatically retry, so one logical call bills at most once.
